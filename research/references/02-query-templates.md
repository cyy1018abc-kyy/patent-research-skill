# 02 检索式模板

## 硬规则

1. **主检索式最多 3 个 AND 子句** —— 再多命中数会塌缩到个位数。
2. **IPC 是后置过滤器**，不写进检索式。
3. **每个子查询必须窄。** CNIPA 每次只回 3 条，宽检索等于浪费机会。
4. **子查询之间角度必须不同**；不得用同义改写凑数。

## 合法子查询的形状

```
{ label: 短名, abstract: 关键词A and 关键词B and 关键词C }
```

三词组合原则：**领域词 × 对象词 × 手段词**，外加第四角度——**效果词**
（2025 指南二·七 §5.4.2：基本检索要素按技术领域、技术问题、技术手段、技术效果四方面提取）。

| 位置 | 作用 | 示例（燃料电池 / 气液分离） |
|---|---|---|
| 领域词 | 限定技术领域 | 燃料电池 |
| 对象词 | 限定作用对象 | 气液分离 / 排水 / 排放 |
| 手段词 | 限定实现方式 | 毛细 / 分级 / 双阈值 |
| 效果词 | 从技术效果角度再开一批子查询 | 防淹 / 抗水淹 / 水管理 |

效果词子查询与手段词子查询**角度不同**（满足硬规则 4）：手段词找「怎么做」，效果词找
「做到了什么」——审查员检索口径里这是两组独立要素，漏掉效果角度是池子判满仍 FAIL 的隐性原因之一。

**关键词三层完善**（对齐指南二·七 §6.3）：每个核心概念按三层展开后再进子查询——

| 层 | 展开什么 | 示例（气液分离） |
|---|---|---|
| 形式 | 词性 / 单复数 / 错拼变体 | 分离 / separator / gas-liquid |
| 意义 | 同义 / 近义 / 反义 / 上下位 | 分离 / 排出 / 脱水 / 挡水 |
| 角度 | 技术问题措辞 vs 技术效果措辞 | 「防止水淹」vs「提高排水效率」 |

**双层技术领域**（指南二·七 §5.3）：先检**所属领域**（按权利要求的功能/用途与实施例定位），
再扩展**功能/应用类似领域**——按**本质功能**找，不按名称：比如「燃料电池水管理」的本质功能是
「微尺度两相流控制」，同功能领域（雾化、冷凝、微通道散热）里可能出现最毒的对比文件。
应用场景子查询（下节第 3 条）是它的子集，不是全部。

## 坏例与好例

| 坏例 | 问题 | 好例 |
|---|---|---|
| `燃料电池 and 控制` | 太宽；3 条全是无关 | `补氧 and 燃料电池 and 前馈` |
| `燃料电池` | 无对象词、无手段词 | `dead-end and 阳极 and 燃料电池` |
| `燃料电池 and 燃料电池 and 燃料电池` | 同词重复 | 无意义，删掉 |
| `(A or B) and C and D and E` | AND 超过 3 个 | 拆成多个子查询 |

## 子查询怎么累积

一个轴通常需要 **10–28** 条子查询才能把池子养到可判规模。来源：

1. **从轴的每个技术特征出发**，各写 1–2 条
2. **从同义词族出发**：中文 / 英文 / 缩写 / 旧称（先过关键词三层：形式 / 意义 / 角度）
3. **从应用场景出发**：车用 / 航空 / 航天 / 船舶 / 固定式
4. **从技术效果出发**：把效果措辞当独立角度写子查询（对齐 2025 指南四要素口径）
5. **从功能类似领域出发**：本质功能相同的不同领域（双层技术领域第二层）
6. **从已判文献回填**：反复出现的词变成新子查询

## 「检索够不够」怎么判

不要凭感觉，看两个数：

| 指标 | 含义 | 目标 |
|---|---|---|
| **每轴 relevance≥4 的文献数** | 该轴的有效覆盖 | ≥10，且**缓冲 ≥+3** |
| **池子是否 100% 已判** | 还有得判吗 | 全判完才能说「不是判得不够，是搜得不够」 |

> **为什么要有缓冲**：阈值正好压在 10 时，一次重判或一次排除就把门顶红。
> 出现过「建了缓冲又被自己的复核掀翻」的事故——因为缓冲建在被误判的文献上。

## 与工具的关系

```powershell
# 看一个轴的子查询计划
python -m patentkit search-plan --axis N1

# 只跑新增的子查询（历史日志名不冲突）
python -m patentkit fetch-cnipa --axis N1 --from-library --only 18,19,20
```

子查询注册在 `01_search_plan/query_library.yml` 的 `cnipa_batches` 下；
**只在末尾追加，永不重排已有编号** —— 否则历史日志对不上号。

## 覆盖规划（内核 0.4.0 起有工具）

「检索够不够」不再手工对表——`queryplan` 把本节的两个指标变成每个轴的数字：

```powershell
python -m patentkit queryplan             # 全轴：已登记 vs 已执行子查询、缓冲、缺口
python -m patentkit queryplan --axis N1   # 单轴
python -m patentkit queryplan --apply     # 把建议骨架追加进查询库（只追加，不动既有编号）
```

它回答三件事：

1. **登记了没跑**：`cnipa_batches` 里登记了但日志里找不到对应执行的子查询——先跑完再谈补查；
2. **缓冲状态**：每轴 G-S-02 verified 计数与缓冲（口径同 [05](05-acceptance-gates.md)），
   零缓冲/缓冲不足直接给补检索结论；
3. **措辞漂移**：目标技术要素组（topics 概念表）里**任何一个关键词都没出现在已登记子查询中**的组
   ——这是「池子判满仍 FAIL」的最常见原因。对未覆盖组给出确定性骨架
   （`label: auto-<组名>`，取组内前两个中文关键词），`--apply` 追加进查询库后
   **人工措辞检查**再跑——骨架是导航，不是检索式成品。
