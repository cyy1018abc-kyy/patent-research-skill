# 多技能矩阵拆分设计（v3.0 方向，待立项决策）

> 对应升级清单 P2-13。**这是一份决策文档，不是已实施的架构**——拆分动的是发布工程
> （安装器/CI/跨客户端测试），风险集中在「配对发布」上，故留到 v3.0 单独立项。

## 为什么拆

2.5.0 的技能已经覆盖「调研 → 交付物 → （方法论层）交底/OA」。单一 SKILL.md 的
description 要承载全部触发词，触发精度会随能力面变宽而下降；按场景拆成子技能，
每个 description 只对自己的场景负责（对标 patent-disclosure-skill 的 9 技能矩阵）。

## 拆分方案（推荐 C）

| 方案 | 内容 | 优点 | 风险 |
|---|---|---|---|
| A. 单仓多技能 | 一个仓库、一个发布包，内含多个技能目录 | 安装一次全装；跨客户端测试复用 | 包变大；不用的技能也常驻 description 池 |
| B. 多仓多包 | patent-research / patent-drafting / patent-oa 各自独立仓 | 隔离最干净 | 配对发布 ×3；术语表要跨仓同步，最容易漂移 |
| **C. 单仓、按技能目录 + 共享内核**（推荐） | 本仓库保持单一事实源；`patent-research-skill/` 下按 `research/` `drafting/` `oa/` 三个技能目录重组，references 09–11/13 就位到对应技能；内核 patentkit 不动；发布器按「全量包」与「单技能包」两种产物出 | 术语表/evals/CI 一份；安装器已支持多目录；回退容易（目录重组可逆） | 构建器要改产物清单；需要一次性迁移 PR |

## 拆分后的技能边界（草案）

| 技能 | 触发场景 | 携带的 references | 共享物 |
|---|---|---|---|
| patent-research（现有） | 检索/查新/门禁/证据链 | 01–08、glossary | glossary.md、_env.py、patentkit |
| patent-drafting | 交底书/申请文件/权要/改稿 | 09、10、13 | 同上 + 04（硬约束） |
| patent-oa | 审查意见答复 | 11、12 | 同上 + 03/04 |

## 必须一起动的配套（决策时逐项过）

1. `build_skill_release.py`：支持多技能产物 + manifest 结构升级（schema 2）；
2. evals：按技能拆评测集，validate_evals 锚定各自的 SKILL.md；
3. 术语一致性检查：glossary 提到仓根共享位；
4. 安装器：`-Client both` 安装 N 个目录；卸载语义（全卸/单卸）要定义；
5. 跨客户端测试矩阵 ×3；
6. CHANGELOG 与迁移指南（用户侧从 2.5.0 升 3.0 的目录变化）。

## 决策点（需要仓库所有者拍板）

- 是否接受方案 C（单仓多技能目录 + 双产物发布）？
- v3.0 的时间窗（建议在真实使用 2.5.0 一个迭代之后）；
- patent-oa 是否并入 patent-drafting（OA 答复与改稿闭环耦合度高，可先两技能起步）。
