# 04 证据等级制度

> **这是理解其它一切的前提。** 不理解本文件，会把"自述"当成"证据"。

## 为什么需要这个制度

一个专利调研项目最容易出的问题不是"检索得少"，而是**分不清哪些结论有据、哪些只是自己说的**。

历史上出过这样的事：项目曾以 `asserted`（memory 注入的记忆）为依据自评"五门全 PASS"，
实际 `verified` 侧是 **0**。按现行制度，那份成绩保留在 `≥asserted` 列，
但**不构成 PASS 依据**。

## 三个等级

| 等级 | 含义 | 判据 | 能否用于 PASS |
|---|---|---|---|
| **`verified`** | 库内有**可回放的原始产物** | `raw/` 文件存在、非空、`capture_mode=live` | ✅ **只有这个能** |
| `attested` | 外部数据 + 库内 sha256 绑定 | 有 `evidence_ref` 与 `evidence_sha256` | ❌ |
| `asserted` | 纯自述（人写的、模型写的、记忆里的） | 无其它要求 | ❌ |

**关键**：`attested` 证明的是"我们看的是哪一份文件"，不证明"文件内容是对的"。

## 三列单调

每个门禁按三个等级各算一次：

```
verified（最严）  ≤  ≥attested  ≤  ≥asserted（全部）
```

列是**单调**的，越左越严。**判定（PASS/FAIL）只看最严的 `verified` 列。**

这样设计的原因：历史成绩不必删，可以一直保留在宽列里追溯；但它不能让人冒充通过。

## 落到实处的几条

1. **候选的 `evidence_level`** 由它的来源决定：
   - 来自 `raw/` 原始响应的 → `verified`
   - 来自库外文档（稿件）+ sha256 → `attested`
   - 人工填写 / 模型生成 / 记忆 → `asserted`
2. **模型代判一律记 `asserted`**，且必须在 `review_note` 写明「【模型代判】」+ 理由。
3. **`capture_mode` 决定 run 的证据等级**：
   - `live` → 数据来自实时 DB，可作为 `verified`
   - `retrospective` / `memory` → **只能 `asserted`**
4. **数据是真的 ≠ 判断是真的**。
   D 列来自实时检索（`verified`），但"这 5 篇是近端对比"是判断（`asserted`）。
   两者必须分开标，不可混为一谈。

## 自检问题

在写下任何结论前，问自己：

- 这条结论背后有 `raw/` 文件吗？路径是什么？
- 如果没有，它的证据等级是什么？我标对了吗？
- 我是不是把"我记得"当成了"有据"？

答不上来，就不要写 PASS。
