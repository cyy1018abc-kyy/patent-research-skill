# 20 · 实用新型撰写与交付（4.3 / 内核 0.11.0）

> 本文件定义**实用新型**申请在结构化撰写管线（D1–D8）中的专用规则：申请类型、权项类别、
> 结构附图导入与人工确认，以及实用新型的审计码与交付门。
> 本技能产出底稿并标注缺口，**不判断能否授权、不替代专利代理师**；
> 启发式检查一律只提醒，最终由人判断。

## 1. 法规口径（只写能给出出处的规则）

| 规则 | 出处 | 落地 |
|---|---|---|
| 实用新型 = 对**产品的形状、构造或者其结合**所提出的适于实用的新的技术方案 | 《专利法》第 2 条第 3 款 | 权项只能是产品类（D-020/D-021）；方法/材料/软件本身的改进不是保护客体（D-023 提醒） |
| 实用新型专利申请的初步审查（含保护客体、说明书附图、摘要附图等形式与明显实质缺陷） | 《专利审查指南》第一部分第二章 | 附图必备（D-022 / E-013）；有附图的申请指定摘要附图（E-014） |

> 《专利法实施细则》2023 年修订后条号有变动：本文件**不臆造条号**；需要引用细则条文时，
> 以官方现行文本核对后再写入，核对记录登记到 `docs/policy-log.md`。

## 2. 申请类型与权项类别

```powershell
# 生成实用新型撰写计划（附图需求=结构示意图，不生成方法流程图需求）
python -m patentkit draft plan --idea IDEA-001 --type utility_model --apply
```

- `drafting_plan.application_type`：`invention`（缺省）| `utility_model`。旧计划无此字段 = 发明，**无需迁移**。
- `claim.claim_category`：`product` | `method` | `use`（可选）。从属权项不写时**继承**所引权项的类别。
- 实用新型的**每个独立权项必须声明** `claim_category: product`（D-021）。
- 摘要附图：在计划里写 `abstract_figure: FIG-1`（交付前必须指向已有附图）。

## 3. 结构附图：人工绘制 → 导入 → 人工看图确认

实用新型附图要表示产品的形状、构造或者其结合。自动渲染器只能画框图/流程图，**画不出机械结构**，
所以结构类附图一律由人绘制（CAD 导出的黑白线条图，PNG），再导入登记：

```powershell
# 导入（默认 dry-run）：复制到 07_drafting/figures/external/，按 SHA-256 钉住
python -m patentkit figures import FIG-1 .\drawings\fig1.png --title "图1 产品整体结构示意图" --parts "1=壳体,2=盖板,3=卡扣" --apply

# 人工看图确认（绑定「文件哈希 + 附图标记清单」）
python -m patentkit figures review FIG-1 --by inventor --apply
```

- `--parts` 必须列出图中**每一个附图标记**及部件名称（`标记=名称`，标记 1–3 位数字）；
  它是图文一致性（附图标记 ↔ 说明书）核对的依据。
- `figures plan` 遇到「结构示意图/剖视图/立体图/主视图…」类需求**不会自动生成**，只在
  `needs_import` 中列出——用框图冒充结构图会误导审阅者。
- 换文件或改标记清单后，旧确认自动失效（F-016），必须重新 `figures review`。

## 4. 审计码与交付门（实用新型相关）

| 代码 | 级别 | 适用 | 含义 |
|---|---|---|---|
| D-020 | error | 实用新型 | 方法/用途类权项（含从属权项继承的类别）不属于实用新型保护客体 |
| D-021 | error | 实用新型 | 独立权项未声明 `claim_category: product` |
| D-022 | error/warn | 实用新型 | 计划无附图需求（error）；全部附图都是流程图/状态机（error）；含流程图（warn）；尚无附图（warn，交付时 E-013 拦截） |
| D-023 | warn | 实用新型 | 原子措辞含「方法/步骤/工艺/配方/程序/算法…」等，提示可能是方法/材料/软件特征——**由人判断**（用已知方法名称限定产品是允许的） |
| D-024 | error | 全部类型 | 从属权项声明的类别与所引权项不一致 |
| D-025 | error/warn | 全部类型 | `abstract_figure` 指向不存在的附图（尚无任何附图时为 warn） |
| F-015 | error | 外部附图 | 文件缺失、不是 PNG，或导入后被改动（哈希不符） |
| F-016 | warn | 外部附图 | 尚未人工确认，或确认已过期；交付构建会直接拒绝 |
| E-013 | error | 实用新型 | 交付件没有附图 |
| E-014 | error | 实用新型 | 有附图但未指定摘要附图，或摘要附图不在交付件中（发明为 W-003 warn） |
| E-015 | error | 外部附图 | 交付后外部附图被替换/改动或失去人工确认 |

## 5. 实用新型交付流程（D 线差异点）

1. `draft plan --type utility_model` → 在计划里补 `abstract_figure`；
2. 原子只写**形状、构造、位置、连接关系**；权项全部 `product`；
3. 结构附图走第 3 节「导入 → 确认」，说明书「附图说明」逐图引用（图1、图2…）；
4. `draft audit` 零 error → `draft gate --to review_draft`；
5. `deliver build` → `deliver check`（E-013/E-014/E-015 必须为零）→ 人工 `deliver sign`
   → `draft gate --to release_ready`。DOCX 首行写「实用新型名称」，并单列「摘要附图」。

## 6. 边界

- 本工具不判断「是否属于实用新型保护客体」的最终结论：D-020/D-021 只基于声明的类别，
  D-023 只是措辞提醒；结论由代理师确认。
- `release_ready` 仍只是内部交付门；CNIPA XML 未实现，不得宣称「可直接提交」。
- 附图的清晰度、线条规范、标记位置等需人工逐图复核；导入只保证文件与标记清单被钉住。
